# MagicDesk 2.2

Draft, not released. Final packaged-build acceptance, Windows CI, NixOS desktop
acceptance and comparative benchmarks remain release gates. Current per-OS
results are in the [distribution matrix](../../native/guest-exec-lab/validation-matrix.md).

## Shroot Performance

- Lazy AArch64 SVC entry accelerates eligible calls in stock programs, including
  glibc, musl, static executables and Go. No libc compilation, private loader,
  registry or additional OCI layer is required. Distribution files are unchanged.
- Shroot Base remains the ordinary interception path for unsupported sites,
  unavailable capabilities and explicit diagnosis. Installed seccomp filters
  revoke accelerated entry and retain kernel syscall admission; sandboxed
  execution does not imply the unfiltered direct-entry speedup.
- Filesystem and descriptor handling reduce repeated path work, metadata
  bookkeeping and cross-thread replies. Writable overlays share the native-name
  path while retaining hardlink, copy-on-write, permission and watch semantics.
  These runtime improvements also benefit Shroot Base.

## Networking

- Shroot launches share network selection, port publication and DNS policy.
  Docker and Podman can use the supported logical nftables bridge/NAT path,
  including TCP/UDP published ports, outbound traffic and container peers.
  Docker's documented nftables configuration no longer requires a userland proxy.
  Unsupported rules remain explicit errors, not successful no-ops.
- IPv4/IPv6 launch configuration, named network definitions and logical netlink
  state share the same network owner. Networkd, address/route changes, supported
  DHCP operations and UDP multicast use that model without modifying Android's
  network configuration. External IPv6 connectivity still requires a working
  host route. Named definitions do not connect independent supervisors.
- TCP-reset REJECT is supported. Unsupported UDP/ICMP rejection rules fail at
  admission rather than silently becoming DROP and causing network timeouts.

## Linux Compatibility And Graphics

- Legacy X11 MIT-SHM can attach Shroot's virtual SysV shared memory to the
  embedded server through a scoped FD bridge. SteamOS's software profile uses
  Zink over Lavapipe without disabling shared-memory presentation.
- Compatible Turnip setups support hardware browser composition through the
  shared DMA-BUF path. Flatpak GL extensions and Snap content bundles reuse the
  recipe's private Mesa build after compatibility checks; installation does not
  compile a second Mesa just to package those bundles.
- The guest FUSE service supports document-portal export, access and revocation,
  rofiles-fuse and SquashFUSE workflows. Append, private mappings and supported
  watches share the filesystem owners. Coherent writable shared mappings and
  independent-supervisor provider transfer remain outside its contract.
- Process and service compatibility includes logical NOFILE/NPROC limits,
  extended `clone3`, binfmt_misc, proc/sysfs views and disk-backed tmpfs/ramfs.
  Cgroup controller limits remain permissive. Ramfs/tmpfs are not host-memory
  filesystems, and persistent read-only remount does not revoke already acquired
  writable descriptors or mappings.
- Signal delivery, debugger checkpoints, JIT repair and descriptor completion
  share explicit ownership. Fixes address interrupted builds and Qt tooling
  without disabling JIT or application sandboxes.
- Stock Snap can run with reduced confinement when it detects unavailable
  AppArmor. Shroot does not implement strict AppArmor isolation. Browser,
  container and init success remains scoped to the recorded distribution tests.

## Linux Installation

- Recipes prefer official ARM64 rootfs archives where available. SteamOS uses
  Valve's ARM64 recovery image, updates its configured repositories and provides
  nested Plasma launchers with software or compatible Turnip graphics.
- NixOS has an official-image recipe and declarative Plasma configuration.
  Activation uses NixOS tooling; complete graphical acceptance is still pending.
  Recipe-owned compilation disables Nix build sandboxing only for that command,
  without changing the installed user's normal Nix sandbox policy.
- One compiler job setting, four by default, applies to Mesa/Turnip, KWin, Weston
  and Nix recipe builds. Dependency installation precedes compilation in the
  existing environment. Lazy SVC acceleration works automatically with stock
  distribution libraries and needs no setup.
- Current network copies the selected executor's Android DNS addresses once.
  Resume retains the environment and DNS without downloading the rootfs again.
  Source extraction does not attempt to restore archive owners on Android build
  bindings; image imports retain their metadata-preserving behavior.
- Administrative setup uses the selected root account's home rather than the
  image user's home. GUI setup initializes a missing system Flatpak repository
  before user-session notifiers start; existing repositories are left alone.
- See [installation and resume](../shroot.md#linux-installer) and
  [syscall acceleration and Base](../shroot.md#syscall-acceleration).

## Console And Desktop

- Android shell commands use bundled upstream mksh, with persistent command
  recall across new interactive sessions. Termux and guest Linux keep their own
  shells. History does not preserve a live PTY across APK replacement.
- Console entry points share the existing-session picker without allocating an
  unwanted session. Phone console windows are visible in Running and Recents.
- Desktop property handling separates common Android policy from the authorized
  setter available on a particular firmware.
- Shizuku-provider settings accept an ordered semicolon-separated package list.
  Startup selects the first installed package; changes apply on restart, without
  silently switching provider after a permission or service failure.

Existing format-17 Linux environments are retained. Shroot remains experimental
and is not a security boundary for untrusted images or programs. See
[coverage and limits](../shroot.md#coverage-and-limits).
