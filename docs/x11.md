# Embedded X11

MagicDesk embeds an X server and presents Linux applications in ordinary Android
windows. The standalone Termux:X11 APK is not required. The local `x11-runtime`
module supplies Android integration; the native engine comes from the
[Termux:X11 fork](https://github.com/mekhontsev/magicdesk-x11).
Choose an executor for programs and keyboard data. **Termux** needs its
external-command support, `RUN_COMMAND`, `xkeyboard-config` and the desired
X applications. **Shell / root** uses the existing authorized command service
and an explicit XKB directory from a prepared Linux environment; it does not
require Termux. The local X server runs as MagicDesk's app UID, never root.

The **X11** tool opens the session manager. **New X11 session** creates a named
session, optionally with a startup command, and opens its desktop in a separate
window. Selecting a retained session only selects it in the manager;
**Open X11 desktop** opens its whole desktop, while **X11 windows** opens a
chosen client window. Session controls are available in the X11 manager.
**Run command** runs another command with that session's `DISPLAY`
and `XAUTHORITY`. Commands are explicit shell scripts in the selected execution
environment. A full X desktop needs its own window manager/session command.
Closing a whole-session Android window retains the server and its clients; reopen **X11**
and select the session, then **Open X11 desktop**, or select its remembered
recipe in Start to reopen it directly.
**Stop X11 session** terminates that server. Separate
sessions have separate X sockets, authorization cookies and input focus.

**Close Desktop** releases Android task ownership, not X11 sessions: hosted
applications become independent fullscreen windows on the same live display.
Display-loss recovery returns the hosts to the phone. Neither transition
requests `WM_DELETE_WINDOW` or restarts the Linux program.

## Applications

Start includes graphical applications discovered from the selected Termux's
`$XDG_DATA_HOME/applications` (default `~/.local/share/applications`) and
`$PREFIX/share/applications`. User entries take precedence, including hidden
entries that mask installed launchers. The catalog is refreshed when Start is
opened; it does not scan through a privileged filesystem service.
Symbolic links to readable `.desktop` files are included under their launcher
paths; broken links and linked subdirectories are skipped.

Start loads `Icon=` artwork separately from catalog discovery, through the same
Termux endpoint. A process-local cache retains hits and misses, deduplicated by
icon name and cleared when the selected endpoint changes; removed catalog names
are evicted. Reopening Start or scrolling does not read icon files. Small PNGs
are looked up in user/Termux `hicolor` application directories and `pixmaps`, or
at an absolute `Icon=` path. This is a bounded bitmap fallback, not a full icon
theme engine: SVG/XPM-only and oversized icons retain the generic terminal icon.
Results arrive in batches below Termux's result-size limit and are decoded off
the UI thread to at most 96x96 pixels. Visible icons update in place without
rebuilding the grid or disturbing input. No X server, shell/root permission,
image-conversion process or additional library is needed. Changed artwork at an
unchanged name is reloaded on the next MagicDesk process start.

Launching one creates a dedicated X session and an ordinary Android window for
its first mapped client. A splash, or a window not yet classified by X properties,
can occupy that launch host until the first identified application window arrives.
The host then replaces its borrowed output without closing the server or creating
another Android task. An empty gap after startup content does not by itself end
the session; the existing startup deadline still bounds unsuccessful launches.
Repeating the same recipe reuses its live host through
the shared application-placement service; New window explicitly starts another
session. A retained whole-desktop session without a host receives a new viewer,
not a second server. After a session ends, its Recent entry starts the saved
command again. Opening files supplies new arguments and is not replaced by a
focus-only operation. The session presents additional main windows separately,
without requiring the previous host to be focused. It follows the last verified
host placement; a background launch without a live Activity requires existing
shell access. Otherwise the window remains available in **X11 windows**.
X transients and toolkit popups are composited with their
owner, not treated as independent Android applications. MagicDesk's **Close window**,
Alt+F4 and MCP `close_task` send `WM_DELETE_WINDOW` before removing an individual
host. Its Android window and taskbar entry remain while the client asks to save
or refuses to close; native window-destruction observation completes closure.
**Force stop app** on an X11 host disconnects the owning X client without a save
dialog. All windows sharing that connection can close, including another document
in the same LibreOffice instance. It does not force-stop MagicDesk or Termux.
A whole-desktop host's Force stop instead stops that entire X11 session.
The system caption's cross can remove the Android task directly, without an
Activity close-request callback. Its lifecycle sends the graceful request and
reopens a surviving client in a new Android host, using that host's last verified
display, ownership and mode. Windowed bounds are read from the closing Activity's
current `WindowMetrics`, not its last resize/focus callback; moving a window alone
does not necessarily deliver those callbacks. The replacement also retains the
confirmed caption inset until the new root publishes its own insets. Child padding
then defers to Android's normal inset consumption, without a timed wait or counting
the caption twice. The task ID changes and a brief disappearance
is possible. A surviving host of the same X window prevents duplication. Recovery
requires available shell access and the original destination; failure is reported
without a retry loop, and the client remains available in **X11 windows**.
Whole-desktop viewers are not reopened. Session stop and Exit cancel recovery.
MagicDesk does not intercept caption coordinates or delay for a guessed response. A
dedicated application session stops after its last catalogued window is gone.
A whole-session host instead retains its server until explicit Stop.
Client titles and `_NET_WM_ICON` images appear in task descriptions, the taskbar
and application pickers. Missing or invalid icons retain the X11 tool fallback;
no Termux icon-file access is required.

Managed window position, size and mode use the common application-state store,
keyed by Android profile, host tool and semantic launch recipe. Calc, Writer and
other launchers retain independent geometry, including when their windows share
one X server. Equivalent recipe copies use the same key as Recent; a document
title, XID or Android task ID does not create another preference. An explicit
launch rectangle takes priority. Windows without a known recipe use default
placement and do not overwrite other applications' saved state.

Firefox and GIMP can run concurrently without a separate Termux:X11 APK or
an X window manager. Applications still retain their own single-instance and
profile-locking rules. Full X desktops use a separate retained session with
their window manager; container launch commands must expose this session's
X socket and Xauthority inside the container. The integration does not install
or configure a proot/chroot distribution automatically.

For example, LibreOffice's general launcher and its Writer/Calc launchers share
one user-profile process. A command may forward to an already running instance
instead of using its new `DISPLAY`; it can exit successfully without creating a
window on the new server. For an application recipe with `StartupWMClass`,
MagicDesk can bind the original launch host to a newly observed matching window
in an existing application session, then close the unused server. Matching
requires the same executor identity, a successful command, and exactly one
unpresented window and pending launch. Existing windows, whole-desktop sessions
and ambiguous matches are excluded. This standard class hint is not a causal
token; a command that only raises an existing window cannot be correlated this
way. Startup diagnostics retain the no-window failure for unresolved launches.
MagicDesk does not replace application profiles or force separate processes.

Custom `.desktop` entries select `X-MagicDesk-ExecBackend=termux` or `shell`
and `X-MagicDesk-X11Mode=application` or `desktop`. Their `Exec` is
expanded as desktop-entry arguments, with literal arguments quoted before
execution, rather than implicitly interpreted as shell syntax. Use explicit
`sh -c` for a script. Terminal entries instead omit the X11 mode and use their executor's PTY.
`X-MagicDesk-X11Mode=desktop` selects a whole-session view for a desktop/window
manager command; it is also accepted in the selected Termux's application
catalog. The default `application` mode presents individual client windows.
Both modes use the common private `.desktop` Recent store. Recipes retain the
command and executor configuration; each launch resolves its runtime identities.

## Linux Environments

The **New command app** editor (Console toolbar or Desktop/Files context menu)
offers **Linux (Termux)** launchers for installed `proot-distro` environments or
custom entry scripts, and **Linux (Shell / root)** for prepared environments
entered through the authorized command service.
Choose **X11 application** with a guest command such as `xfce4-terminal`, or
**Linux desktop** with `xfce4-session`. **Terminal** opens the guest shell in
MagicDesk Console, without X11. Graphical recipes require `dbus-run-session`
in the guest. Termux recipes are saved in its user applications directory;
Shell recipes are Desktop `.desktop` files and require shell access to save.
Both refresh Start after saving and work without managed Desktop.
Both share an optional Linux user, guest working directory, deletion and Recent.

### Chroot Without Termux

Prepare a rootfs externally and provide an entry script. MagicDesk is not a
distribution installer or container manager. The example
[`chroot-entry.sh`](../scripts/examples/chroot-entry.sh) uses an isolated mount
namespace and requires an already-authorized UID 0; adjust its rootfs path and
install it at an executable location. It accepts the same user, guest directory
and command arguments as the Termux entry-script adapter. A terminal needs no
XKB files. Graphical recipes additionally need `dbus-run-session` in the guest
and an Android-visible XKB path, for example `/data/local/linux/alpine/usr/share/X11/xkb`.
MagicDesk stages bounded keyboard data in its own private cache, off the UI thread.

The script receives `DISPLAY`, `XAUTHORITY`, `MAGICDESK_X11_RUNTIME` and
`MAGICDESK_X11_TMPDIR`. It exposes the session socket and cookie inside the
guest; no fixed X display number or disabled authentication is needed.
Imported files use `/tmp/magicdesk-x11/content`. For graphical Linux recipes,
the script also binds the packaged `MAGICDESK_GUEST_FILES_HELPER` executable at
`/tmp/magicdesk-guest-files` and preserves `MAGICDESK_GUEST_FILES_SOCKET` and
`MAGICDESK_GUEST_FILES_TOKEN`. The supplied command starts this helper **after**
selecting the guest user. It opens exported files inside that guest; the renderer
does not acquire root or interpret host rootfs paths.

Terminal, individual-client and whole-desktop presentation reuse the same
retention and Android-placement paths as Termux. Stopping a shell-backed X11
session cancels its owned command transports; scripts must retain their child
lifetime rather than daemonizing out of it. GPU drivers, audio and additional
guest mounts remain distribution configuration, not MagicDesk setup.
See [command entries](desktop-entries.md#command-entries) and the
[entry-script contract](desktop-entries.md#custom-linux-entry-scripts).
The explicit wrapper below remains useful for custom guest setup or chroot.

An installed `proot-distro` container can use the same whole-desktop launch
path. Install the desktop **inside the container**, not in Termux. For example,
a minimal Ubuntu XFCE environment needs `xfce4-session`, `xfwm4`, `xfce4-panel`,
`xfdesktop4`, `xfce4-terminal`, `thunar` and `dbus-x11`. Check the container's
preferred terminal: installing XFCE does not necessarily replace an existing
`x-terminal-emulator` alternative.

A Termux wrapper for a container named `ubuntu` can use:

```sh
#!/data/data/com.termux/files/usr/bin/sh
set -eu
: "${DISPLAY:?Launch through MagicDesk X11}"
: "${XAUTHORITY:?MagicDesk X11 authorization is required}"
exec proot-distro login --isolated --shared-tmp \
    --bind "$MAGICDESK_X11_RUNTIME:/tmp/magicdesk-x11" \
    --bind "$MAGICDESK_GUEST_FILES_HELPER:/tmp/magicdesk-guest-files" \
    --env "DISPLAY=$DISPLAY" --env XAUTHORITY=/tmp/magicdesk-x11/Xauthority \
    --env "MAGICDESK_GUEST_FILES_SOCKET=$MAGICDESK_GUEST_FILES_SOCKET" \
    --env "MAGICDESK_GUEST_FILES_TOKEN=$MAGICDESK_GUEST_FILES_TOKEN" \
    --env XDG_CURRENT_DESKTOP=XFCE --env XDG_SESSION_TYPE=x11 \
    ubuntu -- /tmp/magicdesk-guest-files -- /bin/sh -c '
        set -eu
        umask 077
        XDG_RUNTIME_DIR=$(mktemp -d /tmp/magicdesk-xfce.XXXXXX)
        export XDG_RUNTIME_DIR
        trap '\''rm -rf -- "$XDG_RUNTIME_DIR"'\'' EXIT
        dbus-run-session -- xfce4-session
    '
```

Make the wrapper executable. In Termux's `~/.local/share/applications`, add an
ordinary `Type=Application` entry with its absolute path as `Exec`, a `Name`,
`Terminal=false`, `X-MagicDesk-ExecBackend=termux` and
`X-MagicDesk-X11Mode=desktop` and `X-MagicDesk-X11FileEnvironment=ubuntu:root`.
The file-environment identity must distinguish the entry environment and guest
user, not individual applications in the same environment. The Linux editor
generates it automatically. Start discovers the entry; Recent remembers the recipe.
The wrapper inherits the allocated display and authorization rather than using
a fixed `DISPLAY`, disabling X authentication, or launching another X server.
`--shared-tmp` exposes Termux's temporary directory, including the X socket;
this is an integration boundary, not a security sandbox. Each launch has its
own D-Bus session and runtime directory. No host root is needed, even when the
container presents a simulated root user. Desktop packages retain their own
HiDPI settings and Linux service requirements; a PRoot session is not a booted
Linux system with systemd, power management or a system D-Bus service.

## Clipboard And Drag-And-Drop

The focused X11 window shares Android's clipboard: UTF-8 text, HTML, PNG images
and file selections work in both directions. Clipboard access follows Android
focus permissions; unfocused sessions do not continually read the phone's
clipboard. Copying again creates a new selection, even for the same file URI.

Drag text, images or files between Files/Android apps and an X11 window, or
between independent X11 sessions. The receiving application must support the
offered format. Transfers use **Copy**, not Move: a drop never authorizes deletion
of the source. The same adapter serves individual X windows and whole Linux
desktops. Desktop mode is not a prerequisite; Android must provide a visible
source and drop target.

Files and images cross process boundaries through seekable descriptors and
read-granted content URIs, not Binder byte arrays. X11 INCR handles large
selection transfers. Text/HTML reads are bounded to 1 MiB each, each file/image
to 128 MiB, and a file selection to 64 items. Drag text over 32 Ki characters
(text and HTML combined) is exported as a text/HTML document for other Android
apps, avoiding oversized drag-event Binder parcels. Transfers between MagicDesk
X11 windows retain the original text/HTML formats.
Within one X server, drops retain the original selection and its native formats,
including application-specific names with quoted MIME parameters.
External Android drags negotiate XDND at drop, when the payload and URI grants
become available. Materialized host-to-host drags retain hover negotiation;
X clients cannot block themselves by reading an Android selection before its grant.
Drop hit testing respects X11 input shapes, including transparent compositor
overlays in full Linux desktops. Optional protocol tracing uses Android's
`log.tag.X11Content=DEBUG`; it records transaction identifiers, not payloads.

Android files are copied into the receiving X session's private content
directory and remain readable until that server stops. X11 exports use the
shared, read-only generated-content provider with its 24-hour retention and
256 MiB storage limit. The per-session import limit is also 256 MiB. Existing
exports are not silently evicted to admit a new transfer. Directories, remote
file authorities and non-regular files are not exported.

Ordinary Termux clients resolve files under the X server's own identity.
Graphical Linux recipes instead declare one file environment per X session.
The guest helper opens local regular files with that guest user's credentials
and passes read-only descriptors over an authenticated session-scoped Unix socket.
The same route serves PRoot and prepared chroot, full desktops and individual
applications. It does not run shell commands or elevate on a clipboard/drop request.
Imports expose only that session's shared content directory inside the guest.
Text/HTML/PNG selection data does not require a shared filesystem namespace.

Custom wrappers must implement the explicit guest-file contract above; setting
only `--shared-tmp` is insufficient. Paths are never guessed from a distribution
name, and an unavailable guest bridge never falls back to opening the same path
in Android. Different environments/users are excluded from cross-session launch
correlation. One X session must not mix unrelated guest filesystem namespaces.
The manager's raw host-command action is unavailable for these guest-bound
sessions; launch guest applications through their Linux recipes instead.

## Boundaries

- `X11Execution` captures the server identity separately from the client executor.
  Termux launches through RUN_COMMAND. Shell-hosted servers use an app-UID
  `app_process` and staged XKB data; client commands use the authorized service.
  `CommandExecution` and `OperationResources` own command completion and
  cancellation, including completion before a resource handle is registered.
- `X11LaunchSpec` builds the launch environment and private Xauthority input.
  Xorg allocates a free display atomically through `-displayfd`; the host does
  not guess display numbers or poll sockets. Readiness is announced at Xorg's
  `ddxReady`, after allocation and screen/input initialization, not during
  `OsVendorInit`. TCP listening is disabled; `-noreset` retains the server
  generation between client connections.
- `X11Sessions` owns pending admissions, Binder lifetimes, ready renderers and
  explicit shutdown. `MagicDeskRuntimeService` retains this shared service
  independently of Desktop and closes it on runtime exit.
- `X11LaunchTracker` correlates committed window catalogs with pending launches
  on the main thread, within the existing startup deadline. `X11WindowPresentation`
  owns presentation reservations, per-host replacement placement and the last
  verified Android destination for newly discovered sibling windows.
  New windows in the same executor wait for a pending class-based launch to
  resolve, since toolkit classes can change after mapping. Failure or the
  existing startup deadline releases these reservations; there is no settling timer.
  The launch Activity can rebind its borrowed output to another session without
  moving either X window. Live recipe associations identify an individual X
  window, so reopening Calc cannot select Writer's host in the same process.
- `X11SessionReceiver` accepts only the captured server UID with a fresh,
  pending-session nonce. Android 14's attributed broadcast delivers the sender
  identity. A cancelled or unknown admission cannot start Xorg. Server owner
  death requests normal X shutdown, including socket cleanup.
  The host registers the receiver before launching `X11Server` with its APK as
  CLASSPATH. The `attach` announcement carries the server Binder, session and
  token; the host validates these and retains the server with its owner Binder.
  Only retention starts Xorg. The subsequent `ready` announcement supplies the
  allocated display. Every server Binder operation checks the exact host UID.
  [X11LaunchSpec](../app/src/main/java/io/github/mekhontsev/magicdesk/X11LaunchSpec.java)
  defines the package identities, native library, content directory, shared-file
  policy, XKB path and application-mode environment. The nonce and Xauthority
  cookie authorize different connections and must remain private.
- Startup has a 60-second deadline, not a retry loop. The host revokes pending
  admission on failure; the server also exits if it never acquires an owner.
- Long-lived X11 commands continuously drain stdout/stderr with bounded storage,
  preserving the command's exit status. Termux uses a 16 KiB diagnostic tail;
  shell commands reuse the shared command capture limit.
- MagicDesk's `X11Session` owns one renderer, socket and Present consumer per
  X server. Its outputs borrow Android Surfaces and select the root X screen
  or an XID. One HandlerThread serializes commands and connection teardown;
  callbacks use the host's Executor. Frame callbacks report availability/size,
  not every animation frame. Reconnect replaces the socket while retaining the
  server and clients. Surface release is acknowledged by the renderer; stopping one
  connection does not terminate another connection's EGL resources.
  Density and client-close commands are asynchronous; focus callbacks do not
  wait for the X server. Native command output uses bounded, nonblocking socket
  writes. Surface replacement waits for the renderer's resource-release
  acknowledgement. Pixel-lock liveness belongs to the exact connection, and
  disconnect cancels lock waits before waiting for renderer detachment. Socket
  publication and frame presentation do not hold the shared pixel mutex.
- `X11ApplicationLaunch` converts X11 presentation into the existing Android
  launch request. `ToolApplications.openSibling` inherits the source task's
  current ownership, not merely the presence of Desktop on that display.
- `X11ManagerActivity` owns session selection and controls. It never borrows an
  output or acquires clipboard/input/density ownership. `X11Activity` is only a
  client/desktop viewer; it does not own the X server. Both use the existing
  Android placement gateway, including the caller's managed/independent mode.
- `X11HostBinding` owns one viewer's session subscription, borrowed output,
  content exchange, density registration and fullscreen responder. It releases
  fullscreen and content transactions before unregistering the host and releasing
  the Surface. `BuiltInWindowRegistry.CloseHandler` routes explicit requests to
  the host before Android removal or Desktop focus handoff. Client closure is
  asynchronous and retains the borrowed output; forced closure uses the same
  ordered command channel with client-disconnect semantics. Recreation/replacement
  retains the client. Direct Android task removal sends a graceful close request
  only if the client still exists, then releases the old binding before scheduling
  one replacement host. Recovery rechecks the live catalog and other hosts, without
  a timer or extra task observer. Observed destruction never sends another request.
  Exit disables all session presentation before finishing Activities, including
  sessions temporarily without a host. Finishing a whole-desktop viewer retains
  its server. Late callbacks cannot revive a closed binding. These lifetimes do
  not merge the separate size, density, clipboard and fullscreen ownership policies.
- `HostedSurfaceView` owns Android Surface, keyboard and IME lifetimes;
  `HostedPointerInput` owns pointer gestures through `HostedSurfaceOutput`.
  It sends normalized coordinates, semantic
  buttons and scroll axes; `X11SurfaceOutput`/`X11InputEncoding` alone map these
  to X11 button numbers, wheel clicks and keycode limits. Focus loss releases
  held input.
  Pointer routing uses each MotionEvent's source, tool, contacts and classification,
  not the InputDevice capability mask or a firmware/model check. Mouse buttons,
  ordinary wheel axes and stylus strokes remain direct. Finger taps defer their
  button until release; one-finger touch drags commit after Android touch slop or
  long-press timeout. Two-finger contacts and Android-classified touchpad scrolls
  produce wheel steps without holding the primary button. Pixel deltas accumulate
  using Android scroll factors, including classified gesture history; finger
  arrival/removal rebases the centroid without resuming a one-finger drag.
  Raw touchpad coordinates move the pointer relatively; mouse-source coordinates
  remain absolute. Content drag handoff transfers button ownership to the drop
  protocol. Focus/output/geometry loss cancels pending contacts and delayed presses.
  The bounded `hosted_input/pointer_route` event samples at most 32 distinct
  device-ID/event-shape pairs per host, sharing one budget across all devices,
  without pointer positions or repeated motion logging. It helps
  distinguish raw contacts, mouse events and classified scrolls in device reports.
  `HostedViewport` supplies the aspect-fit transform between host pixels and
  normalized content coordinates, shared by pointer and drag input. It retains
  out-of-content coordinates for backend policy; X11 performs its existing clipping
  and wire quantization. Geometry changes recompute the transform, not each event.
- `HostedContentExchange` owns Android focus, scoped clipboard observation,
  drag gestures and temporary URI grants through `HostedContentBackend`.
  Offers and drops are opaque transactions carrying `AndroidContentPayload`
  and Android MIME types, not XIDs or protocol target names. `X11ContentExchange`
  owns output filtering, selection ownership, XDND operations and same-server
  offer reuse. `X11ContentTransfer` converts payloads to X targets and streams
  provider/file content in the appropriate execution domain.
  Releasing an older host cannot disable its new clipboard owner. Source tags
  prevent clipboard feedback without a second global clipboard or polling.
  The Android host cancels pending reads, releases drag grants and detaches the
  backend before its borrowed renderer output is released.
- MagicDesk's `X11DataExchange` and the fork's native selection/XDND engine own negotiation,
  transfer IDs, descriptor ownership, INCR and event-driven drop completion.
  Clipboard and drag selections are independent. Bounded queues and protocol
  deadlines reject abandoned requests; connection changes invalidate pending
  work. `X11FileExchange` owns file import/export and delegates guest paths to
  `GuestFileBridge`. The small static `magicdesk_guest_files` executable runs
  inside the guest and supplies descriptors, independent of libc distribution.
  Its worker retains no command stdio, sleeps on socket reads and exits when
  the server closes the connection. Server shutdown cancels blocked bridge I/O
  without taking the request lock. No privileged service is acquired per transfer.
  `X11Execution` owns private-directory cleanup: the Termux launcher's EXIT trap
  or the local server process owner releases it after shutdown or failure.
- `X11Server` is MagicDesk's executor-side entry point. Its own Binder contract
  authorizes the exact host UID for connection, shutdown and file access.
  `X11ProcessContext` creates only an executor-package Context, not an Application.
  `X11ServerLifecycle` serializes ownership, readiness and stop-before-ready.
  Java/JNI belongs to MagicDesk; the native engine's `embedded.h` contract is
  independent of Java classes and Android application policy.
- Native window callbacks publish complete catalog snapshots. Surface families
  use Composite pixmaps and shared Damage tracking, with an atomic frame commit
  per output. No periodic Android task scan is introduced.
- On-demand `X11WindowInspection` uses the same family membership policy but
  includes actual children and unmapped/input-only windows. Native inspection
  runs on the X server thread; the host then reads Android placement on the UI
  thread. It creates no output, changes no focus and is not a widget tree.
  [MCP inspection](automation.md) exposes the bounded result through
  `x11.inspect_window`, including explicit missing/truncated states.
  `X11Session` admits at most four pending inspections, correlates replies by
  serial and bounds each reply to five seconds. Cancellation, reconnect and
  closure release pending requests; late replies cannot populate another read.
- Output/input/window commands across Java/JNI/native have named operations; only the native
  transport packs operation numbers and overloaded wire fields. All commands
  share the same ordered connection queue. Native argument structures are
  stack values, not new per-input or per-frame heap allocations. The window
  catalog separates metadata from `X11WindowManagement`: the versioned client
  request and confirmed host state remain distinct. State objects are published
  on catalog changes, never as per-frame rendering callbacks.

An X display number, an XID, a renderer output ID and an Android display ID are
distinct identities. Opening X11 does not create an Android display, claim
input routing, acquire HOME or start managed Desktop. The Termux route requires
no privileged service. Interactive launches can use Android-accessible secondary
displays; background placement and existing-task transfers require the shared
privileged launcher.
Local Start, installed-app discovery, saved Recent entries and the X11 manager
remain usable with only Termux integration. Reopening a live host on its current display shares
the terminal's ordinary own-task activation path; it does not query the global
privileged task catalog or create a Desktop runtime. Local input and clipboard
exchange stay within the ordinary Android host APIs.

## Graphics and Limits

Dedicated application sessions advertise a minimal EWMH host window manager.
Client `_NET_WM_STATE_FULLSCREEN` add/remove/toggle requests flow through the
native window catalog to `HostedFullscreen`, which requests ordinary Android
immersive presentation. Managed tasks use the existing Desktop transition
controller and restore their prior window geometry; ordinary fullscreen
Activities need no privileged service. Whole Linux desktops retain their own
window manager and do not export these requests into the Android host.

Requests and confirmed state are distinct. A session-wide request serial rejects
stale acknowledgements, including reused XIDs. Only one Android host responds
for an X window; additional views do not compete. Android mode callbacks and
layout confirm entry/exit, and a manual restore withdraws the X request. No
Activity relaunch, synthetic keypress, or additional task poll is involved.
The built-in window registry supplies explicit application intent to the same
Desktop reconciler on firmware without requested-insets observations. Losing
focus alone is not a request to leave fullscreen.

An individual hosted window follows its Android Surface size, constrained by
the client's `WM_NORMAL_HINTS` minimum and maximum dimensions (`PMinSize` and
`PMaxSize`). Fixed-size windows, including splash screens, retain those dimensions;
the renderer centers and aspect-fits their content instead of resizing their X
surface. Valid limits also apply after a client changes its saved geometry or
size hints. Missing or malformed limits fall back to the host size, bounded by
the native geometry limit. Resize increments and aspect-ratio hints are not yet
applied. Multiple views of the same XID have one
size owner: the most recently resized view; the others preserve aspect ratio.
An individual hosted window is kept inside the X root's
input-reachable area, including after client position changes; Composite
rendering alone does not make off-screen pixels reachable by the X pointer.
This does not reposition windows in a whole-desktop output, where the Linux
window manager owns placement. In individual views, mapped dialogs and menus are
kept within the main window's content bounds where their size permits. Oversized
transients retain their toolkit size and extend the composite canvas; the whole
family is aspect-fitted into the Android Surface. Closing them restores the main
view's scale. Rendering, pointer and drag coordinates use that same canvas.
The virtual X screen retains exact pixel dimensions, including widths not
divisible by eight. Physical CVT timing alignment must not shrink it below a
dialog's bounds and cause repeated screen reconfiguration and input latency.
Placement follows X geometry/property/map events, not frame-driven polling or
application-specific rules.
Existing focus inside an X child of a dialog is preserved, not mistaken for a
different application's focus. This keeps modal confirmations above their owner
when a toolkit uses a hidden child for keyboard input.
The Android pointer is used; application-specific X cursor images are not
presented yet. Catalog titles are bounded to
255 UTF-8 bytes; icons are bounded to 64x64 ARGB pixels; an output family is
bounded to 256 layers.

The graphics path retains upstream AHardwareBuffer/EGL support. Linear DRI3
DMA-BUFs can use an optional Vulkan EXA copy accelerator. It loads the system
Vulkan driver lazily, verifies external-memory support, and imports buffers
without replacing the client's storage. Unsupported drivers, ordinary shared
memory and failed imports retain Xorg's CPU copy. Vulkan is not a startup
requirement and adds no bundled driver or library.

Imported resources live with their pixmaps. GPU completion and the existing
renderer lock serialize access to destination HardwareBuffers. When the driver
requires more trailing allocation space than the producer supplied, only the
fitting rows are imported; a small suffix uses a staging upload. This is not a
claim of zero CPU copies on every driver or geometry. There is no screenshot
loop or vendor-specific graphics backend.

## Interface Scale

X11 follows its host window's logical Android density: 160 Android DPI maps to
96 X11 DPI. Moving a window to another screen or changing that screen's density
updates the X server without scaling a captured bitmap. For multiple windows of
one X session, the most recently focused host selects its common density;
background windows cannot overwrite that choice. A retained session keeps its
last density while no host is open.

Long-press or right-click an installed Termux application in Start to set its
interface scale (50-200%, relative to the display). The session manager exposes
the same control for its selected session. Installed application's preferences
are saved by executor identity and desktop-entry path (the selected package for
Termux, the captured service UID for Shell), privately within
the Android profile. Ad-hoc sessions keep their scale for that session only.
These are Linux preferences, not overrides for the MagicDesk Android package;
they require neither shell access nor managed Desktop.

Dedicated application servers publish atomic XSettings updates (`Xft/DPI`,
`Gdk/WindowScalingFactor`, `Gdk/UnscaledDPI`) as well as X resources and RandR
dimensions. GTK uses integer widget scaling with adjusted font DPI; Qt and
other toolkits decide which standard settings to honor. Applications with
their own forced scale or cached startup DPI may still require a restart.
Whole Linux desktops receive initial X resources and physical-DPI updates but
retain ownership of their settings daemon. MagicDesk does not overwrite a
replaced resource database or reclaim XSettings from a Linux manager.

## Platform Support

The minimum is API 34. Lint and compilation do not replace Android 14
device testing, which is still pending. The fork's
[embedding contract](../vendor/magicdesk-x11/docs/embedding.md) describes the
library protocol and build requirements; [licensing](licensing.md) covers
corresponding source distribution.

## Verification

`HostedPointerInputTest` covers gesture/button ownership, scroll directions,
fractional accumulation and cancellation. With a debug APK,
`am instrument -w io.github.mekhontsev.magicdesk/.HostedInputInstrumentation`
also exercises real Android MotionEvents through both SurfaceView entry points.
Run instrumentation with no active work: Android replaces the application process.
It does not start Desktop, acquire display input or require a physical touchpad.

Build and unit-test commands are in the [runtime README](../x11-runtime/README.md#verification).
Exercise individual applications and whole desktops without managed Desktop,
with both Termux and Shell/root executors. Check concurrent sessions, input/IME,
clipboard and file drag, DPI, fullscreen, output recreation, normal shutdown and
owner-death cleanup. See the [validation matrix](testing-backlog.md).

The test-only `x11-runtime/example` hosts two outputs. Launch it with a fresh
`token` (at least 24 characters) and `leftSession`/`rightSession` extras;
matching session IDs share a server. Optional `leftWindow`/`rightWindow` select
XIDs; zero selects the root screen. Start corresponding `X11Server` processes
with those identities, the example host package and the server's executor package.
Its uncompressed native library is loaded from
`<installed-base.apk>!/lib/<abi>/libXlorie.so`. Never reuse production tokens.
Re-deliver SINGLE_TOP with `token`, `session` and `command=reconnect`, `recreate`
or `stop` to exercise connection and output lifetimes. Destruction of this test
Activity stops its servers; production viewer destruction retains whole sessions.
